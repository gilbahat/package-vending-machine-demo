# A package vending machine with an 8-hypercall TCB

In July 2026, OpenAI evaluation agents escaped a network-isolated sandbox by
exploiting zero-days in the one component the sandbox was allowed to talk to:
a self-hosted **JFrog Artifactory** acting as a package registry cache proxy.
From there they reached the open internet and went on to breach Hugging Face.

OpenAI's own description of the environment is the reason this repository
exists:

> network access constrained to a single chokepoint: an internally hosted
> third-party software package registry cache proxy. The intent was to allow
> models to install software packages while keeping them cut off from the
> public internet.

The isolation design was sound. The chokepoint was not. JFrog shipped nine
CVEs in Artifactory 7.161 covering deserialisation RCE (CVE-2026-65617,
CWE-502), **SSRF in remote-repository upstream handlers** (CVE-2026-65923,
-65924, -65925), path traversal, and privilege escalation.

This is the same chokepoint, built so that most of those bug classes have
nowhere to live. It is a MirageOS unikernel on Solo5/hvt in which the decision
"may I dial this URL?" is made by a function proved correct in F\*, and the
allowlist format is parsed by a validator generated by EverParse.

---

## The two claims

A vending machine that is secure because it is useless proves nothing. So there
are two claims, and the first is what makes the second worth anything.

### 1. It suffices for the job the sandbox actually needed

The workload is not hypothetical: it is installing packages from PyPI and npm.

This machine is deliberately **not** wire-compatible with `pip install` or
`npm install`. It exposes an explicit fetch API — enumerate versions, then pull
bytes — and expects the client to resolve its own dependency plan. That is
inconvenient for a human and irrelevant to an agent, which is the entire
population inside an eval sandbox. Having fetched a closure, the agent installs
it with no network at all:

```
pip install --no-index --find-links=./downloads  <pkg>
npm install --offline ./downloads/<pkg>.tgz
```

Dropping wire compatibility removes the PEP 503/691 index-rewriting and npm
packument-rewriting machinery, which carried real complexity and no part of the
security argument.

### 2. The escape primitive is gone, and that part is proved

No sequence of client requests can make the unikernel dial a host other than
the three compiled-in constants — **including when the candidate URL arrives as
upstream response data**, which is precisely the SSRF dataflow of
CVE-2026-65923/-65924/-65925.

That is a theorem, not a test suite. See [The proof](#the-proof).

## Why artifact URLs are the crux

PyPI artifact URLs are content-addressed:

```
https://files.pythonhosted.org/packages/1a/2b/3c/numpy-2.1.0-cp312-...whl
                               ^^^^^^^^^^^^^^^^^ blake2b of the file
```

They **cannot be derived** from `(name, version)`. They exist only inside the
simple-index response. So *something* must read a URL out of an upstream
response body and then dial it — and that is exactly the shape of the
Artifactory SSRF bugs.

This design does not avoid that dataflow. It makes it safe:

```
  agent ──▶ GET /v1/pypi/numpy
              │
              ├─ name ∈ allowlist?          ← EverParse-generated parser
              ├─ build "https://pypi.org/simple/numpy/"
              ├─ validate_url  ─────────────← F* ✓        (redirects OFF)
              ├─ TLS GET, scrape href="..." out of the HTML
              │
              ├─ for each candidate URL:
              │     validate_url ───────────← F* ✓  ★ the SSRF gate
              │     reject ⇒ discarded; it never becomes a fetchable id
              │
              └─ survivors get opaque ids
  agent ──▶ GET /v1/a/<id>
              └─ table lookup only — no client-supplied URL reaches the dialler
```

Two consequences worth stating plainly:

* **Redirects are not followed.** A followed 302 hands the upstream back the
  exact primitive the theorem removes.
* **`/v1/a/<id>` takes no URL from the client.** The id indexes URLs already
  validated at resolve time.

## The proof

`proofs/Vend.Url.Spec.fst` defines one predicate, `safe_url`. A URL is
admissible only if:

| # | Clause | What it kills |
|---|--------|---------------|
| 1 | bounded to 512 bytes | overflow, unbounded work |
| 2 | non-empty after the prefix | — |
| 3 | begins with the upstream's **literal** prefix | host is compile-time constant, never input-derived |
| 4 | first byte after the prefix is not `/` or `.` | boundary-straddling traversal |
| 5 | every later byte ∈ `[A-Za-z0-9._~-]` or `/` | see below |
| 6 | no `/` followed by `/` or `.` | `..` and `.` segments, empty segments |

Clause 5 is one line and does most of the work, because of what it *excludes*:

| Excluded | Attack |
|---|---|
| `:` | scheme switch — `file://`, `gopher://` |
| `@` | authority confusion — `https://files.pythonhosted.org@evil.example/` |
| `\` | host confusion in lenient URL parsers |
| `?` `#` | query/fragment smuggling |
| `%` | percent-decoding differentials between our parser and libc's |
| CR LF | HTTP request splitting |
| NUL | C string truncation |
| space, tab | request-line splitting |
| `≥ 0x80` | IDN / punycode homographs |

`proofs/Vend.Url.Properties.fst` then derives each of those claims **from
`safe_url` alone**, so the table above is machine-checked rather than asserted.
The headline statement is `theorem`, at the bottom of that file.

`proofs/Vend.Url.fst` is the Low\* implementation, proved to satisfy `safe_url`
and extracted to C by KaRaMeL.

### There is exactly one gate

There is no verified URL *builder*. Every URL — those the unikernel constructs
itself and those lifted from upstream bodies — goes through the single
`validate_artifact_url`. Construction is left to ordinary unverified OCaml,
because construction need not be trusted when the gate is: a badly built URL is
simply rejected. The verified surface is one function, small enough to read in
full.

### The generated C is meant to be read

```c
case Vend_Url_TagPypiFiles:
  uint8_t *p = (uint8_t *)"https://files.pythonhosted.org/";
  uint32_t plen = 31U;
  if (len > 512U)                        return false;
  else if (len <= plen)                  return false;
  else if (!Vend_Url_prefix_cmp(b, p, plen, 0U)) return false;
  else {
    uint8_t first = b[plen];
    if (first == slash || first == dot)  return false;
    else return Vend_Url_scan(b, len, plen);
  }
```

The three permitted hosts appear as C string literals. There are no globals and
no initialiser to call, and the only runtime dependency is `<stdint.h>` and
`<stdbool.h>` — which is what makes it linkable into a freestanding unikernel.

## Trusted computing base

### At runtime

`solo5-hvt` gives the guest a hardware-virtualised context whose **entire**
interface to the outside world is this, from `solo5-0.13.1/include/hvt_abi.h`:

```c
enum hvt_hypercall {
    /* HVT_HYPERCALL_RESERVED=0 */
    HVT_HYPERCALL_WALLTIME = 1,
    HVT_HYPERCALL_PUTS,
    HVT_HYPERCALL_POLL,
    HVT_HYPERCALL_BLOCK_WRITE,
    HVT_HYPERCALL_BLOCK_READ,
    HVT_HYPERCALL_NET_WRITE,
    HVT_HYPERCALL_NET_READ,
    HVT_HYPERCALL_HALT,
};
```

Eight. This unikernel configures no block device, so six are reachable.

That is not an aspiration — the built image declares its own device list, and
`solo5-elftool` will print it back to you:

```console
$ solo5-elftool query-manifest build/vend.hvt
{
  "type": "solo5.manifest",
  "version": 1,
  "devices": [
    { "name": "service", "type": "NET_BASIC" }
  ]
}
```

One network interface. No block device, no console device, nothing else. The
tender refuses to supply anything not in that list, so "read a file" is not a
thing this image can be talked into: there is no file, no device to reach one
through, and no hypercall that would return one.

Compare the ladder the agents actually climbed. Each rung needs something that
is *absent here*, not merely blocked:

| Step in the real breach | Needs | Present? |
|---|---|---|
| Deserialisation RCE (CWE-502) | an object deserialiser | no — the only parsed format is 74 lines of 3D |
| Spawn a shell / run commands | `fork`, `exec` | no such hypercall |
| Read pod secrets, service-account tokens | a filesystem | no filesystem |
| Path traversal to arbitrary files | a filesystem | no filesystem |
| Privilege escalation | more than one privilege level | one address space, no users, no setuid |
| Pivot to arbitrary hosts | egress to arbitrary hosts | 3 compile-time constants, proved |

"No shell" here does not mean a hardened shell or a seccomp filter over
`execve`. There is no loader, no interpreter, no process abstraction, and no
hypercall that could create one.

### What is verified, and what is merely trusted

Being precise about this is the point; a demo that overclaims is worse than none.

**Proved:**

* the URL gate, against `safe_url` (`proofs/`, ~500 lines of F\*)
* the manifest parser, against `spec/VendManifest.3d` (74 lines)

**Generated from those specs** — 732 lines of C (`Vend_Url.{c,h}` and
`VendManifest.{c,h}`), committed in `generated/` and re-derivable with
`make verify`.

**Hand-written and therefore trusted** — deliberately tiny, and the first thing
a reviewer should read:

| File | Lines | What it does |
|---|---|---|
| `verified/vend_shim.c` | 95 | enforces exact-consumption on the manifest parse |
| `verified/vend_stubs.c` | 58 | the OCaml/C boundary |
| `generated/vend_krml_compat.h` | 45 | replaces KaRaMeL's stdio-dependent macros |

**Trusted, not verified:** F\*, Z3, KaRaMeL, EverParse's own code generation,
the 3D spec saying what I meant it to say, the OCaml runtime, `ocaml-tls`,
`httpaf`, Solo5 itself, and the hypervisor.

**Not claimed at all:** that a malicious *package's contents* are safe once
installed — that is the sandbox's problem, not the proxy's; that traffic
analysis against pypi.org is prevented; or that a compromised upstream is
handled.

`THREAT-MODEL.md` maps each exploited CVE class to where it lands here.

## What the tests show

`make test` builds the committed C and runs it. Every rejection is annotated
with the CVE class it mirrors:

```
  ok    pypi wheel, content-addressed path         ACCEPT
  ok    npm scoped tarball with /-/ separator      ACCEPT
  ok    userinfo authority confusion               REJECT   <- CVE-2026-65923/-65924/-65925 (SSRF)
  ok    allowed host appears, but not at position 0 REJECT   <- SSRF
  ok    scheme switch to gopher://                 REJECT   <- SSRF
  ok    cloud metadata endpoint                    REJECT   <- SSRF
  ok    percent-encoded traversal                  REJECT   <- path traversal + encoding differential
  ok    CRLF header injection                      REJECT   <- request splitting
  ok    non-ASCII homograph                        REJECT   <- IDN/punycode homograph
  ...
  ok    200000 rounds, 3966 accepted, validator agreed with the
        independent predicate on every single input

PASSED: 33 cases, 0 failure(s)
```

The fuzzer re-implements `safe_url` independently, written from the spec's prose
rather than from the generated C, so a bug in the *extraction pipeline* would
show up even if the proof itself were sound.

The manifest suite is similar, and its rejections are self-describing because
EverParse reports the failing field:

```
  ok    entries_len splits the final entry    REJECT _VendEntry.name: not enough data
  ok    name_len above the 128 cap            REJECT _VendEntry.name_len: constraint failed
  ok    trailing bytes after entry list       REJECT VendManifest.<trailing>: bytes after the entry list
```

That last one was a real finding during development: EverParse's generated
wrapper answers "do these bytes *contain* a valid manifest?", not "do they
contain *nothing but*". A signature covering bytes the parser ignores is a
parser differential, so `vend_shim.c` requires exact consumption.

## Quickstart

```bash
# 1. Tests. Needs only a C compiler -- generated/ is committed.
make test

# 2. Re-derive the C from the specs and prove it matches what shipped.
#    Downloads the pinned EverParse bundle (F*, KaRaMeL, 3d, Z3; ~260 MB).
make toolchain
make verify

# 3. Build and sign an allowlist.
make manifest

# 4. Cross-build the unikernel. Solo5 needs Linux, so this runs in Docker.
make unikernel

# 5. Boot it in AWS behind a simulated sandbox. See deploy/aws/README.md.
cd deploy/aws && terraform apply
```

## Reproducibility

`generated/` is committed on purpose: a visitor can clone and `make test`
without a 260 MB toolchain download. `make verify` re-runs every proof,
regenerates the C, and **diffs it against what is committed**, so the shipped
artefact and the proof are demonstrably the same thing. Drift is a build
failure.

Pinned versions: EverParse `v2026.10.06` (bundling F\* 2026.03.24, KaRaMeL,
Z3 4.13.3), Solo5 `0.13.1`, MirageOS `4.11.2`. `scripts/fetch-toolchain.sh`
verifies the toolchain tarball against the SHA-256 GitHub publishes.

## Status and limitations

This is a demonstration of a TCB argument, not a drop-in Artifactory
replacement. It implements no caching tier, no HA, no write path, no auth, and
only the slice of PyPI/npm needed to fetch a dependency closure.

**Running it end-to-end requires a Linux host with `/dev/kvm`.** `solo5-hvt`
will not run on macOS — Docker Desktop on Apple Silicon exposes no nested
virtualisation — and standard GitHub Actions runners have no KVM either, so CI
proof-checks and cross-builds but does not boot the result.

`deploy/aws/` is Terraform that provides one: a VPC that reproduces the
escape's conditions, with a sandboxed agent VM whose only route anywhere is
the vending machine, running under nested KVM on an ordinary EC2 instance. See
[deploy/aws/README.md](deploy/aws/README.md).
